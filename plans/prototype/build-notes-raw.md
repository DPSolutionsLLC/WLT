## prayer-items

First slice of Prayer Focus, built from a design conversation that explicitly held this module until agenda items had a real discussion-status field — added in this same pass (see the agendas-status-field note) rather than skipped or faked. Council-scoped, commitment-centric — distinct from Prayer Roll (people-centric, ongoing). Two item types share one list: LINKED (created by marking an agenda item's new heart-icon toggle — any council member with write access can mark or unmark) and PERSONAL (added directly from the Prayer Focus page, no agenda tie). The key architectural point from the design conversation, honored exactly: a linked item has NO independent resolve action anywhere in the UI — isPrayerFocusResolved() reads the parent agenda item's status live and returns true only when it's 'decided'; nothing stores a shadow resolved flag for linked items. Personal items use the app's plain soft-off pattern (resolvedAt timestamp, resolve/reopen). Marking is symmetric with unmarking, with the same 'never delete what someone wrote' rule the Todo module already applies to unassignment: unmarking deletes the linked item cleanly only if nobody's added a private note yet; otherwise it's orphaned (unlinked from the agenda item, kept) rather than destroyed. Private per-user notes are a separate append-only thread per item, never shared with the council, same shape as every other notes log in this app. Linking to the Prayer Roll is a deliberate, separate, explicitly-labeled action ('Add to Prayer Roll') — never automatic — that creates a lightweight Prayer Roll person from the item's text (reusing the Prayer Roll's own find-or-create) and adds them as a quiet entry. Council scope is a simple Bishopric/Ward Council switcher on the page, matching the two agendas that actually exist today; built to extend to individual quorum presidencies once those agendas do. Wired to the pre-existing 'Prayer Items' dashboard tile. Seeded with one linked item (paired with the existing seeded agenda item, now marked for prayer) and one personal item, so both types are demonstrable on load. FOLLOW-UP PASS: two new views added to the existing Bishopric/Ward Council scoping rather than replacing it — All (every item regardless of council) and Personal (non-agenda items across both councils at once). Explicitly did NOT add a third quorum-scoped option the person floated, since no quorum-specific agenda module exists in this app yet — councilScope only ever has two real values (bishopric, ward_council), and inventing a filter with nothing behind it would be worse than not having it. Since All and Personal aren't real creation contexts (there's no single council to attach a brand new item to from either), the add-input is hidden there with a note explaining why, and the underlying submit handler is guarded against being called with a non-creatable scope, not just visually hidden. Card labels made specific — an agenda-sourced item now names which council it came from (Bishopric Agenda / Ward Council Agenda) rather than a generic 'From agenda', most useful in the All view but left on everywhere for consistency.

## timezone-date-parsing-bug-sweep

REAL, SYSTEMIC BUG FOUND AND FIXED ACROSS THE APP, reported directly as one wrong date in Music but not actually confined to Music. The cause: new Date('2026-09-13') — a bare date-only string with no time component — is parsed by the JS spec as UTC midnight, not local midnight. Formatting that straight back out with toLocaleDateString() in any timezone behind UTC (Wyoming/Mountain Time included) rolls it back a calendar day, so a real Sunday can render as 'Saturday' with the wrong date AND the wrong weekday label both at once — exactly what got reported. This app already has the correct fix built and used in dozens of places (parseDateKey, which constructs the Date from its own y/m/d parts via new Date(y, m-1, d) — always local, no UTC step to go wrong) — the bug was only ever a handful of spots that took the shortcut of new Date(someDateKeyString) directly instead. CHECKED SYSTEMATICALLY rather than fixing only the one reported instance: grepped every new Date(<bareIdentifier>) call site in the file (212 total) and individually inspected every candidate whose variable name suggested a stored 'YYYY-MM-DD' key rather than a real Date object or a full timestamp. FOUR REAL INSTANCES FOUND, not one: Music's own per-Sunday editor header (MusicSundayEditor — the one actually reported), Program's per-Sunday editor header (ProgramSundayEditor, identical copy-pasted pattern), Program's public/finalized view (ProgramPublicView's latestKey header — meaning a shared, finalized program link could have shown the wrong date to the whole ward, not just an internal editing view), and Prayer Roll's 'last visited' date on a Visit-Tracker-linked stewardship entry. All four fixed the same way, matching the codebase's own established convention rather than inventing a new one: new Date(dateKeyStr) / new Date(latestKey) / new Date(lastVisitDate) replaced with parseDateKey(...) in each spot. CHECKED AND RULED OUT, not skipped: several other new Date(<name>) sites looked superficially similar but confirmed safe on inspection — refDate (already a real Date object via useState), evDate and scheduledFor (both from datetime-local inputs, which include a time component and so don't trigger the date-only UTC quirk), submittedAtMs (a millisecond timestamp, name says so and confirmed), and a free-text date-string parser (new Date(s) inside a flexible format-guessing helper, intentionally permissive, not the dateKey pattern). NOT A NEW MECHANISM: no new code, no new helper — every fix just switched to the same parseDateKey function already relied on everywhere else in this file, so these four spots now behave identically to the dozens of already-correct call sites around them instead of being a special, silently-wrong case.

## multi-ward-plan

MULTI-WARD / MULTI-STAKE ARCHITECTURE — HELD PLAN, NOT YET BUILT. Fully scoped across a multi-turn design conversation per the project's own design-first convention (scope conversationally, hold as a plan, build only when explicitly run — see ways-of-working). Nothing in this note has been implemented in the prototype; every other module still assumes exactly one ward. This is the plan for the real build, to execute as one coherent pass once run, not to retrofit piecemeal.

THREE-LAYER SHAPE (confirmed)
1. Super Admin — manages the list of units themselves (wards, stakes, and possibly areas/districts above that) and can see/manage Users across all of them. Ward-agnostic by nature; the one role that spans everything.
2. A specific ward — everything built in this prototype so far, but scoped to one ward at a time instead of assumed to be the only one. What exists today is the ward-level setup, duplicated for every ward that adopts the app, each with its own roster and leaders.
3. The switch between them — a ward selector above the existing role selector for Super Admin specifically. Pick a ward, then pick a calling within it, same shape as the existing one-role-hides pattern, just one layer up. Anyone who only belongs to one ward never sees the ward layer at all, same logic already applied to roles.

UNIT HIERARCHY (confirmed direction, not just wards+stakes)
Multi-stake is a real possibility, and possibly areas/districts above stakes too — explicitly uncertain how far it goes, which is itself the reason to design the data model generically now rather than hardcode two fixed levels. Model as a generic "unit" concept: a type (area/stake/ward — matching real church structure, which also has missions/districts as the stake-equivalent for some units), a parent unit reference, and a real unit number (the actual church-assigned number, not an app-invented id). This makes adding a level later an extension of the same structure, not a rebuild. Do NOT build actual area- or district-level admin screens now — only the data shape needs to anticipate them; UI for those levels waits until the need is concrete.

ROLE ASSIGNMENT CARRIES THE WARD, NOT THE ROLE ITSELF
Roles (Bishop, 2nd Counselor, etc.) stay as the reusable templates they already are — never duplicated per ward. The ward lives on the ASSIGNMENT: a Users entry says "this person holds this role in this specific ward," which is also what naturally allows someone to hold different callings in different wards should that ever come up. This means accessUsers (and the underlying access-matrix resolution built this session) needs a real unitId/wardId added to each assignment, not to the role definitions.

ROSTER IMPORT STAYS WARD-LEVEL, OWNED BY THE WARD, NOT SUPER ADMIN
Each ward maintains its own roster, imported and kept current by someone at the ward-admin level (the Executive Secretary, for example) following clear instructions — not something Super Admin uploads or manages centrally. Confirmed directly: this need is explicitly temporary. If the church ever adopts this or something like it and links directly to their own databases, the whole import-a-report mechanism disappears entirely — the app would read live data instead of an uploaded extraction. Because of that, the real build should treat "get the current roster for this ward" as a boundary/interface the rest of the app consumes, never caring whether the answer came from a CSV import or a live API — so that when real integration eventually happens, it replaces what's behind that one boundary, not something scattered across every module that reads a member's name. Real membership record numbers (MRNs) should also be a real field on each member once real unit numbers and MRNs are in play, so identity is unambiguous across wards and survives any future real integration — not just a display name.

WARD IDENTITY ACROSS THE REST OF THE APP — SCOPED, NOT YET APPLIED
Every module built this session (Agenda, Prayer Roll, Music, Program, Visits, Youth Support, Receipts, Callings Sandbox, Calendar, and the rest) currently assumes one implicit ward and would need real ward-scoping once this plan is run — but that application was deliberately deferred, not attempted piecemeal, until the shape above (units, role-assignment-carries-ward, the swappable roster boundary) was settled, per explicit direction not to touch this mechanically before the surrounding design was locked.

SEPARATELY BUILDABLE NOW, NOT BLOCKED ON THE REST
Minimum-two-Super-Admin safety rule: never allow the last active Super Admin to be deactivated or removed. Standard "don't let the last key holder lock everyone out" reasoning, matters most once real accounts exist but the rule itself doesn't depend on multi-ward architecture at all, since Super Admin already exists as a role in what's built. Also raised and worth building alongside it: assigning Super Admin specifically probably deserves more friction than an ordinary role assignment, given it bypasses the entire access matrix — a distinct, more deliberate confirmation rather than the same one-click flow as any other role.

WHAT THIS PLAN DOES NOT COVER
Real authentication/login (still its own separate, previously-flagged requirement). Area/district admin UI. The real LCR/church database integration itself. Any actual UI for creating a second ward or switching between wards — the shape is scoped, the screens are not built.

## ward-import

Real production import/reconciliation module, not a stand-in — this was the first-cut 'lighter' version's intended follow-up, built for real per the original Ward List Import & Reconciliation planning conversation. Matching: matchConfidence() does three-tier confidence on Full Name + Birth Date (high = both match, auto-applied; medium = only one matches, only auto-matched when exactly one candidate — ambiguous mediums fall through to 'new' rather than guessing; low = neither, always new). reconcileImport() buckets an incoming batch into new/changed/reactivate/missing against the current roster. diffFields() compares phone/email/address/household label/class assignment/age/ministering fields for the Changed bucket; a calling-text mismatch is checked SEPARATELY and shown as a distinct integrity-flag callout (ShieldAlert icon) rather than a routine field diff, since calling changes are supposed to originate in the app, not be picked up incidentally from LCR. Review UI: four tabs (New/Changed/Reactivate/Missing), each item has its own checkbox — New and Changed default checked (pre-selected for a normal import), Reactivate and Missing default UNCHECKED (both require deliberate opt-in per the source conversation: reactivation needs its own confirmation, and soft-delete should never happen silently). Apply Import commits only the checked items. Soft delete only — Missing records get status:'inactive', never actually removed; a later import that matches them again surfaces in the Reactivate tab. MOCKED PIECE (the only one): this prototype has no backend, so it can't run real PDF/LLM extraction when 'Upload report' is clicked — that button loads MOCK_LCR_EXTRACTION, the real 357-member roster already extracted from an actual LCR report PDF (see the extraction method noted where that constant is defined), standing in for what a server-side extraction call would return.
