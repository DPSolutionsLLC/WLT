# Phase 8 — Youth Activity Support

Tracking secular youth activities — school sports, performances, academic and community
events — so someone from the bishopric or ward council shows up.

**Depends on:** Phase 7 (reuses the report feed). **Unlocks:** Milestone M5.
**Reference:** [FEATURES.md](../FEATURES.md) §Module 10; [SPEC.md](../SPEC.md) §API Routes → Youth Activities.

> This module has the widest access of any in the app: every ward council member can enter
> activities and log attendance. Keep the surface simple — most users will touch it a few
> times a month, on a phone, in a hurry.

---

## Goals

1. Activity profiles linking youth to their schools, teams, and seasons
2. Calendar import: ICS upload, manual entry, and (stretch) Google Calendar sync
3. Home/away classification driving the coverage model
4. Attendee assignment and self-signup, with uncovered-event alerts
5. Post-activity follow-up reusing the Phase 7 report feed

---

## Step 1 — Activity Profiles

A youth can have several — basketball, choir, debate — each with its own schedule.

| Field | Notes |
|---|---|
| `member_id` | Links to the roster. Category must be `youth` |
| `activity_name` | "Varsity Basketball", "Concert Choir" |
| `school_org` | The school or organization |
| `activity_type` | `sport` / `performance` / `academic` / `community` / `other` |
| `season_schedule` | Free text: "Nov–Feb" |
| `notes` | Free text |
| `entered_by` | Who added it |

| Route | Method | Auth |
|---|---|---|
| `/api/youth/profiles` | GET | Bishopric, YM/YW leaders, ward council members |
| `/api/youth/profiles` | POST | Same — **ward council members can enter activities for youth in their org** |
| `/api/youth/profiles/[id]` | PATCH | Creator, bishopric, or the youth's org leaders |

Emits `youth_activity_added`.

Selecting the youth uses `MemberPicker` with `filter: { category: 'youth' }`. Do not
build a separate picker.

## Step 2 — Calendar Import

Three sources, in order of implementation priority:

**1. Manual entry** — always available, always works. Build this first so the module is
usable before any import exists.

**2. ICS/iCal upload** — the realistic primary path. Most school and league schedules
publish an ICS feed or file.

- Parse with a library; do not hand-roll iCal
- Map `SUMMARY` → title, `DTSTART` → `event_date`, `LOCATION` → location
- **Timezone handling is the hard part.** ICS carries floating times, UTC times, and
  `TZID`-qualified times. Normalize everything to `timestamptz` at import and preserve
  the original in case a fix is needed. A game showing at the wrong hour makes the whole
  feature useless
- Recurring events (`RRULE`) — expand to individual rows, bounded to ~12 months ahead
- Import is preview-then-confirm, like the roster CSV. Show what will be created
- Re-import is idempotent: match on `UID` where present, else title + date

**3. Google Calendar sync** — stretch goal. Needs OAuth, token storage, and refresh
handling. Do not start it until ICS works. If time is short, cut it; ICS covers the need.

`activity_calendars` records the source and `last_synced_at`.

## Step 3 — Home / Away Classification

Every event is `home`, `away`, or `tbd`.

Auto-classify from location text on import: match against the ward's home-area
identifiers stored in ward settings (school names, city, venue keywords). Anything
unmatched is `tbd`.

Auto-classification will be wrong sometimes. Make the badge one tap to change, and show
`tbd` events prominently so someone resolves them.

---

## Step 4 — Coverage Model

The two event types get completely different treatment.

**Home events — in-person support.**

- Bishopric assigns an attendee, or anyone self-adds via `activity_attendees`
- An event within 7 days with no attendee is **uncovered** — emit `youth_event_uncovered`
  to bishopric and the youth's org leaders
- Show uncovered events prominently on the dashboard and the activity calendar
- Emit `youth_support_assigned` when someone is assigned

**Away events — awareness only.**

- No coverage expectation
- Surfaced in a **weekly Monday digest**: "This week: Jake is in Billings for a
  basketball tournament (Fri–Sat)."
- Generated by a scheduled Edge Function, delivered as an in-app notification

Both the uncovered check and the Monday digest run from cron. Make the digest one
notification per recipient summarizing all away events, not one per event.

| Route | Method | Does |
|---|---|---|
| `/api/youth/events` | GET | List with filters: date range, type, status, profile |
| `/api/youth/events/[id]` | PATCH | Update type, status, details |
| `/api/youth/events/[id]/attend` | POST | Self-add as attendee |
| `/api/youth/events/[id]/assign` | POST | Assign an attendee — **bishopric only** |

## Step 5 — Post-Activity Follow-Up

After an event passes, attendees get `youth_followup_prompt`.

They confirm attendance (`activity_attendees.confirmed_attendance`) and log a brief
pastoral note in `activity_logs`.

**Same shared/private split as Phase 7**, with the same rules:

- `activity_logs.shared_notes` — visible to all bishopric
- `activity_private_notes` — separate table, `user_id = auth.uid()`, no override, ever
- Never joined into a list query; never in a notification body

Flagging works identically to visits: emits an agenda item to the executive secretary with
a one-liner only. Emits `youth_followup_submitted` on completion.

---

## Step 6 — Reporting

Reuse `ReportFeed` from Phase 7 with `reportType: 'youth_activity'`. Tiles, tap to read,
auto-mark-read, next-unread navigation, flag for later — all identical behaviour.

If the component needs changes to accommodate this, change it in place and re-verify the
visits feed still works, rather than forking it.

---

## Step 7 — Activity Calendar View

`/youth/calendar` — all youth events, filterable by youth, org, activity type, and
home/away.

Coverage state is the primary visual signal: covered, uncovered, awareness-only. An
uncovered home event within 7 days should be impossible to miss.

Ward council members see the **full** activity calendar per FEATURES.md, not just their
own org's events — they can enter activities for their org but view everything.

Mobile-first: a card list on small screens, calendar grid at `md:` and up.

## Pitfalls

- **ICS timezones.** The most likely source of bugs here. Floating times have no zone;
  `TZID` needs a lookup; DST transitions shift things. Normalize at import, store
  `timestamptz`, test all three forms.
- **Unbounded recurrence.** An `RRULE` with no `UNTIL` expands forever. Bound to 12 months.
- **Digest spam.** One notification listing the week's away events, per recipient. Not one
  per event.
- **Re-notifying uncovered events nightly.** Emit once when it crosses the 7-day threshold,
  and again only if the coverage state changes.
- **Forking the report feed.** Two nearly identical components drift. Parameterize the one.
- **Ward council member scope confusion.** They enter activities *for their org* but view
  the *full* calendar. Two different rules; check both.
- **Google Calendar sync scope creep.** OAuth plus refresh plus error handling is a phase
  of its own. ICS first. Cut Google sync before cutting anything else here.
